**Quick facts:**

**Rendering**
- **Two renderers in one file.** `d3-integration.mjs` branches on the payload: a `"layout":"uml"` object is drawn **statically** — boxes at the model's own `x/y/w/h`, connectors as the polylines the payload carries, `d3.zoom`, and **no** force simulation — while anything else falls through to the force layout as before.
- The JS is a static resource served from `target/classes`; after editing it run `mvn resources:resources -pl domox-webapp -q` (same for `static/css/*.css`). The **browser** caches a static resource by URL (no version key), so an edit can look like a no-op; `spring.web.resources.cache.cachecontrol.no-cache` is configured, and a hard reload is the fallback.
- **`@PropertyLayout(cssClass = …)` is a NO-OP on a `@D3Graph` property.** The extension's `D3Panel` replaces Causeway's `AttributePanel`, and `AttributePanel` is the only place the CSS-class facet is applied. Hook the cell Causeway generates instead — `causeway-<objectType>-<memberId>` (e.g. `causeway-domox-ClassCdd-d3Graph`) — with a `.table …` / `td:has(.d3GraphPanel)` fallback that does not depend on that naming.
- **In a list/table the graph cell is `clipped`, so the SVG's box must be sized to the cell** (`static/css/domox.css` rules 1–5). `d3-integration.mjs` measures `.d3GraphCanvas` at DOM-ready and bakes the result into the SVG `viewBox` *and* the force layout: keep the canvas 700px wide for a correct layout and pin the SVG's own `width` to the visible cell — pin only the height and the graph is laid out around the canvas' centre and clipped away entirely (an apparently empty column).
- The hover popup assumes **(a)** the graph column is the **last** column (`right: 0`) and **(b)** `:has()` support (two rules). Both are load-bearing; a column reorder or a `:has()`-less browser degrades the popup.
- **`Candidate.getObjectType()`** (not `getClass().getSimpleName()`) yields the Causeway object type — the entities were renamed to CRC vocabulary while `@Named`/`@Table`/`candidateType` were pinned, so the class name and the object type differ.
- Node JSON includes `isCandidateColumn` (boolean) — the JS uses it to conditionally draw an underline `<line>` under the bold name. There is **no** `CREATE TABLE` or schema migration for D3 diagrams — it is all client-side SVG.
- **Node click = drill down (ontology payloads only).** A payload carrying `"reSearch":true` (emitted by `RdfGraphDiagrams` when it has nodes) makes a click on a node re-run `Corpora#searchOntologyAsD3Graph` for that node's **label**: a **plain click** `fetch`es `/wicket/ontology-diagram?term=<label>` and redraws the graph **in place**; **Ctrl/Cmd-click (and middle-click)** open `/wicket/ontology-drilldown?term=<label>` in a **new tab**, which redirects to the **full Causeway object page** (`DomainObjectPage.forAdapter(...)` — menu, breadcrumbs, the works). Two Wicket mounts are needed because the JS cannot build a Causeway **view-model** URL itself — its id is a *signed* memento only the framework can mint (an RO oid pasted into a `/wicket/object/…` URL fails with *"Digital verification failed"*) — and the RO API answers a page-originated `fetch` with **401**. CRC payloads (no `reSearch`) are unchanged: a node with `candidateId` opens its entity page in a new tab.

**UML geometry** — the rules; the numbers behind them live in `docs/scratch_pad/UML_LAYOUT_GEOMETRY.md`.
- **Every route is orthogonal, and none of them is the export's own.** `OrthogonalRouter` (Hanan-grid A*) discards the stored bends — they are where a dense diagram's crossings come from, because the model's author drew each connector on its own — and routes each connector around the boxes and the routes already placed, **shortest connector first**.
- **Ports are the middle of an edge — never a corner.** The stored path is used only for *where it attached*: its two ends are clipped to the box edges (the export ends a path ~14 units *inside* the box it points at, and the box is drawn on top — so an arrowhead whose tip sat under the box was painted over), then snapped to the **middle of the edge nearest** the attachment, which keeps the model author's choice of *side* and drops only the corner. A path built from `(0,0)` sentinels, one whose end lands far from both boxes, or one whose endpoint has no rectangle yields no hint, and the edge **facing the box it runs to** is used instead.
- **Several connectors on one edge are spread along it** (`spreadPorts`: `(k+1)/(n+1)` of the way, in the order the model gave them, still clear of both corners). A box's four midpoints are where they would otherwise all attach, and they could not then be told apart.
- **Inheritance edges leave the middle of the sub-class's top edge** and go straight up (`DEPARTURE_STUB` 20 before they may turn; the direction is left free when the sub-class has no room to rise that far). All generalizations into one super-class **merge into one trunk**: the middle of its bottom edge (its top when the sub-classes are above it; a side only when they are level — `TRUNK_VERTICAL_BIAS`), arriving **along that edge's inward normal** for `TRUNK_STUB` (24) units. Only the group's first connector carries `"arrow":true`, and the client draws the marker only when `link.arrow !== false`.
- **A connector label hangs on the middle of the route's longest straight run** — not on the middle of the route, which is almost always a corner, and a label on a corner makes the edge look *indented around it*. It carries a **white halo** (`paint-order: stroke`), because another line often passes over the text.
- **A box is widened to fit its class name** — right when there is room, else left, capped by the neighbouring box — so the diagram keeps **one font size**; a box with no room either way keeps its width and the client shrinks that one label. Wrapping is not an option: most names are compound words with nothing to break on, and many boxes are only 28 units tall.

**Measuring and verifying** — all of it offline: no running instance, no database, no SPARQL endpoint.
- **`mvn -o -pl domox-adapter test -Dtest=UmlLayoutIntegrityTest`** asserts every invariant over the **real** model, and **dumps** each diagram's payload to `domox-adapter/target/uml-payloads/`.
- **`python3 scripts/uml-diagram-report.py --check --payload domox-adapter/target/uml-payloads`** reports the same invariants over that dump — corner attachments, shared attachment points, sideways or short trunks, departures off the top middle, hidden/floating tips, backtracks, strays — and over a **live** instance with `--diagram '<name>'`. `scripts/check.sh` runs both, so the two implementations cannot drift apart.
- **`bash scripts/verify-uml-render.sh`** renders a UML payload in headless Chromium and asserts the **client** half: the boxes, the arrow marker, the legend, a label mid-run with its halo, and that `"arrow":false` draws no marker. Part of `check.sh` + CI.
- **`bash scripts/verify-ui-render.sh`** does the same for the table cell: content actually on screen, popup only over the graph column, row height stable. Part of `check.sh`.
- **Driving a browser by hand: don't use `--dump-dom`.** The Chromium snap shares its profile with the user's own browser, so a second instance silently prints **nothing** (exit 0, zero bytes). Use the CDP pattern both `verify-*-render.sh` scripts already implement: launch with `--remote-debugging-port=0 --user-data-dir=<a path under the repo>` and drive it over the DevTools protocol.
